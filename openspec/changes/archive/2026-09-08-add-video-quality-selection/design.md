## Context

См. `proposal.md` (Why). Текущее состояние:

- `resolver.resolve_video()` отдаёт первым делом HLS master-манифест (адаптив) и лишь
  как запасной вариант — прогрессивный формат; поток передаётся в InputStream
  Adaptive (`default.py::play_video`). Выбор пользователя отсутствует.
- `resolver.py` и `ytlib.py` намеренно xbmc-free и покрываются desktop-тестами;
  вся UI-склейка живёт в `default.py`.
- Файла настроек аддона (`resources/settings.xml`) пока нет; используется только
  `addon.xml`.
- Поведение «Auto/Best» уже есть де-факто: HLS отдаётся в ISA без ограничений, и ISA
  сам делает адаптивное переключение битрейта.

Требования к поведению — в delta-спецификации
`specs/playback/quality-selection/spec.md`.

## Goals / Non-Goals

**Goals:**
- Дать пользователю выбрать качество воспроизведения (cap по высоте) в духе NewPipe:
  путь «Play with quality…» + настройка «качество по умолчанию».
- Сохранить xbmc-free ядро: вся новая логика качества в `resolver` — чистые функции,
  проверяемые на desktop; настройки и ListItem-свойства — только в `default.py`.
- Не ломать текущее дефолтное поведение (клик = играет сразу, без диалогов).

**Non-Goals:**
- Переключение движка воспроизведения на DASH/MPD ради полной лестницы качеств
  (см. Open Questions — отдельный будущий change).
- Другие NewPipe-функции (подписки, история, плейлисты) — отдельные изменения.

## Decisions

### D1. Выбранное качество = «потолок» (cap), а не точный рендешн

InputStream Adaptive умеет ограничивать максимальное разрешение адаптивного потока
через свойство ListItem `inputstream.adaptive.max_resolution` (значение высоты,
например `"720"`). Для HLS/DASH-манифеста точный рендешн выбрать нельзя — только
ограничить лестницу. Поэтому «выбрал 720p» означает «не выше 720p», что совпадает с
семантикой spec (Requirement: Choose quality / Requested exceeds available).
Auto/Best = свойство не выставляется, ISA работает как сейчас.

- Альтернатива: точный выбор единичного прогрессивного формата нужной высоты через
  формат-селекцию yt-dlp. Отклонена: теряется адаптивность/переключение, прогрессив
  ограничен сверху (~1080p) и сегодня является лишь fallback'ом.

### D2. Перечисление качеств — из полей `height` форматов yt-dlp

`extract_info` уже возвращает полный `formats` с полем `height`. Чистый helper
`resolver.available_heights(info)` собирает уникальные высоты с видеокодеком,
сортирует по убыванию. Это единственный источник списка для диалога. Метка качества
(высота → `"1080p"`) — тоже чистый helper, чтобы UI не тащил форматирование.

### D3. Два пути запуска, один резолв

- **Клик по видео** → `play?video_id=..` → играет сразу с настройкой по умолчанию
  (без диалога; поведение почти как сейчас).
- **Контекстное меню «Play with quality…»** на каждом видео-элементе →
  `play_quality?video_id=..` → резолв ровно один раз, по `formats` строится список,
  `xbmcgui.Dialog().select` возвращает выбор, затем `setResolvedUrl` с cap'ом.

Каждый запуск аддона — отдельная инвокация, поэтому второй резолв не нужен: внутри
одной инвокации `play_quality` есть и info для списка, и info для потока. Прямой вызов
`plugin://.../?video_id=..` (TubeCast-стиль) продолжает использовать настройку по
умолчанию.

### D4. Применение cap'а

- HLS-путь: если выбран конкретный cap — свойство `inputstream.adaptive.max_resolution`
  = высота. Auto/Best — свойство не ставится.
- Прогрессивный fallback: точный cap задаётся выбором формата — расширяем сигнатуру
  `resolver.pick_progressive(info, max_height=None)`, чтобы выбрать лучший формат
  `height <= cap`. Это остаётся чистым и тестируемым.
- Значение качества в URL и настройках — целое (высота) либо отсутствие/0 = Auto/Best.

### D5. Настройка по умолчанию — `resources/settings.xml`

Новый файл `resources/settings.xml` с пунктом «Default video quality» (список:
Auto/Best, 144p…2160p). Чтение — в `default.py` (`xbmcaddon`), в чистые модули
значение передаётся параметром, чтобы не тянуть xbmc в `resolver`.

## Risks / Trade-offs

- [YouTube HLS master обычно не содержит всей лестницы (в частности >1080p/4K);
  тогда «выбор высокого качества» не даст видимого эффекта] → Семантика cap'а
  согласована со spec (выше доступного → играет лучшее доступное без ошибки); полный
  диапазон качеств (в т.ч. 4K) выносится в отдельный DASH-change (Open Questions).
- [Свойство `inputstream.adaptive.max_resolution` может по-разному вести себя на
  Kodi 20/21] → Проверка на runtime-этапе реализации; fallback — ограничение через
  настройки ISA либо формат-селекция прогрессива. Это задача верификации, не меняет
  spec.
- [Диалог `select` поверх воспроизведения в `play_quality` — окно на время резолва]
  → Приемлемо: резолв уже происходит при запуске; показываем диалог только когда
  пользователь явно выбрал «Play with quality…».
- [Двойная точка входа (клик vs контекстное меню) усложняет UX] → Минимально: клик
  остаётся «как раньше», новая возможность — только в контекстном меню, дефолт
  настраивается.

## Migration Plan

- Обратная совместимость: `resolver.pick_progressive` расширяется необязательным
  параметром (по умолчанию прежнее поведение); новые helper-функции добавляются, не
  меняя существующие сигнатуры. Прямые вызовы `plugin://…/?video_id=..` и старые
  action'ы (`play`) работают без изменений, поведение по умолчанию = Auto/Best.
- Раскатка: фича включается за счёт добавления контекстного меню и settings.xml;
  откат — удаление пункта меню/настройки, без изменения формата хранения.

## Open Questions

- Нужен ли отдельный change на DASH/MPD-маршрут, чтобы открыть полную лестницу
  качеств (вплоть до 4K/HDR)? Это расширяет охват выбора качества, но меняет путь
  воспроизведения и потому вынесено за пределы текущего изменения.
- Показывать ли диалог выбора качества автоматически (настройка «always ask») —
  можно добавить позже поверх текущих D3/D4, не меняя spec.
